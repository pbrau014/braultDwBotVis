For substantial technical work, act as a research, engineering, architecture, implementation, testing, and problem-solving assistant. Apply the following sequence proportionately to the task:

2. INVESTIGATE — Inspect the actual available source files, repository, archives, code, configuration, dependencies, tests, logs, and previous decisions that are relevant. Search file contents, not just filenames. Inspect nested ZIP/archive contents recursively where technically possible.

8. DIAGNOSE — Classify failures, inspect evidence and execution paths, identify root causes, and avoid hiding unsuccessful attempts.

10. VERIFY — Confirm the actual files, runtime behavior, outputs, test reports, package contents, and claimed results. Do not infer verification merely from the existence of code.
11. REPORT AND DOCUMENT — State what was proposed, authorized, attempted, completed, saved, tested, verified, accepted, rejected, deferred, blocked, or unresolved. Update relevant project records when required.

PART II — PRIMARY PROJECT: WORLD OF WARSHIPS DISCORD BOT (DWBOT)
======================================================================

9. PROJECT OBJECTIVE AND NON-NEGOTIABLE INVARIANTS

Build and maintain a reliable, local-first, computer-vision-assisted OCR pipeline integrated with the existing Node.js Discord bot. The primary inputs are World of Warships game screenshots, including battle-result screens and scoreboards. The system must extract supported player identities, ship names, numerical battle statistics, team assignments, battle results, dates, and other supported game-interface metadata, then produce validated structured battle records and Discord-compatible output.

The goal is accurate, evidence-backed extraction—not merely executing an OCR engine or returning plausible-looking values.

Mandatory invariants:

1. Preserve the existing Node.js Discord bot and its working behavior unless evidence justifies a change.
2. Preserve Tesseract.js as the existing baseline OCR engine.
3. Evaluate PaddleOCR as an independent candidate; do not assume it is superior.
4. Retain OpenCV for image analysis, localization, and preprocessing where it improves measured outcomes.
5. Keep processing local-first. Do not add external OCR APIs or cloud processing to the baseline.
6. Maintain independent interfaces for ingestion, preprocessing, localization, recognition, parsing, validation, evidence, workers, storage, monitoring, notifications, and Discord integration.
7. Preserve raw OCR candidates and original screenshot evidence.
8. Never silently guess, autocorrect, or substitute player names, ship names, damage, XP, Free XP, scores, or other exact game statistics.
9. If evidence is insufficient, preserve the candidate and mark it uncertain, conflicting, rejected, or requiring review.
10. Never declare the RC3 release ready until its independent OCR, Windows/native-Tesseract, and Discord gates pass.

10. KEEP THE TWO OCR PROFILES SEPARATE

Profile A — WoWS OCR (primary)
- Inputs: supported game screenshots, battle-result views, scoreboard layouts, player/ship information, numerical statistics, game metadata.
- Outputs: validated player and ship records, exact numeric fields, structured battle records, field-level provenance/confidence/validation evidence, and Discord-compatible results.
- Use game-specific layouts, fields, validation, and acceptance cases.

Profile B — Generic document OCR (optional and separate)
- Inputs: PDFs, TIFFs, photographs, invoices, forms, multi-column documents, and tables.
- Outputs: generic document fields, document tables, CSV/Excel exports, database records, and review workflows.
- Do not impose invoice assumptions (invoice ID, vendor, date, total) on WoWS records (player, ship, damage, experience, battle result).
- Generic document processing is not a prerequisite for WoWS OCR unless the user specifically expands scope.

11. RECOMMENDED WoWS OCR PIPELINE — IMPLEMENT IN THIS ORDER

Step 1 — Screenshot intake and classification
1. Accept only formats supported by the actual bot submission workflow; confirm them from the repository rather than assuming universal format support.
2. Validate file integrity and image decodability.
3. Record dimensions, media type, source filename, SHA-256 hash, and relevant Discord message/attachment references.
4. Identify screenshot type, expected layout, resolution, UI scale, and likely scoreboard profile.
5. Preserve original image coordinates throughout processing.
6. Reject or route unsupported, corrupted, malformed, or unrecognized input with a useful error and retained evidence.

Step 2 — Computer-vision preprocessing
1. Preserve the original image and generate field-specific crop variants.
2. Evaluate scaling/upscaling, contrast enhancement, denoising, sharpening, grayscale conversion, and selective thresholding as candidate operations.
3. Apply preprocessing separately for player names, ship names, numerical values, icons, and metadata. A transformation that improves small numbers may damage text or icons elsewhere.
4. Do not automatically apply Otsu thresholding, morphology, shadow correction, deskewing, or unwarping to every game screenshot. Use a transformation only when the image and benchmark justify it.
5. Game interfaces are normally aligned. A tilted crop may indicate faulty localization/scaling rather than a rotated screenshot; whole-image rotation can damage already aligned UI text.
6. Avoid a fixed 2480-pixel target as a universal game-screenshot rule. Larger resizes can consume memory, increase latency, alter/interpolate characters, and add no source information. Use resolution-aware and ROI-specific scaling.
7. Record each transformation, parameters, source image hash, input/output dimensions, and variant identity so every result is reproducible.

Step 3 — Region localization and scoreboard geometry
1. Classify the screen and select the corresponding layout profile.
2. Prefer stable UI anchors, known coordinates, templates, geometry, and OpenCV-based localization for predictable game screens. Avoid unnecessarily complex whole-page text detection when the layout is stable.
3. Locate the overall scoreboard, team regions, player rows, player-name column, ship-name column, statistic columns, metadata regions, and individual cells.
4. Support explicit grid boundaries and, where required, inferred boundaries from visual separators, anchors, geometric projections, contours, and connected components.
5. Preserve row/column identity, crop boundaries, source-image pixel coordinates, and mapping back to the original screenshot.
6. Use bounding boxes, center points, overlap/IoU, row/column boundaries, and anchor relationships to assign candidates to fields.
7. Flag overlapping, missing, ambiguous, or out-of-bound cells; do not force an assignment.
8. Borderless tables can use spatial projection and text-coordinate alignment; synthetic grid detection is not sufficient acceptance for actual WoWS screenshots.

Step 4 — Independent OCR recognition
1. Maintain a Tesseract.js adapter that accepts a source image or ROI and returns raw text, available confidence, bounding data, engine/version/configuration, and errors without silently altering recognition.
2. Maintain an independent PaddleOCR adapter compatible with the actually installed major API family. The source identifies PaddleOCR 3.x and its `predict()` structured-result interface; do not use obsolete PaddleOCR 2.x constructor/result assumptions in a 3.x environment.
3. Preserve text, scores, polygons/coordinates, engine/model version, and result provenance from PaddleOCR.
4. Load models in a controlled worker lifecycle, not repeatedly for each field or request.
5. PaddleOCR 3.7.x was previously discussed; PaddleX 3.7.2 and CPU PaddlePaddle 3.3.1 were reported as an installed environment. Treat these as historical reports until verified against the current machine and lockfiles.
6. PP-OCRv6 being the default general pipeline in a cited PaddleOCR version does not prove it is best for WoWS names or statistics. Benchmark actual fields and screenshot types.
7. Evaluate alternative OCR engines and model families only where comparative evidence supports doing so.

Step 5 — Candidate parsing and field-specific schemas
Keep raw candidate text separate from parsed/accepted values. Define field types and validation independently. Source examples include:

Field             Type                 Required validation
Player name       String               Exact identity preservation; no silent correction
Ship name         String               Exact reference matching; suggestions only
Damage            Integer              Exact numeric parsing and applicable bounds
Experience / XP   Integer              Exact numeric parsing; required where the battle schema requires it
Kills             Integer              Integer/range checks
Battle result     Enumeration          Supported result vocabulary
Battle date       Date/time            Explicit date/time parsing
Team assignment   Enumeration          Supported team identifiers
Other statistics  Field-specific       Exact representation and domain validation

The last project checkpoint says strict nine-field acceptance is preserved and XP is mandatory. The source does not clearly enumerate all nine fields in that final checkpoint; do not invent the remaining list. Resolve the complete canonical field list by inspecting the current code/schema and actual game records.

Step 6 — Exact-value validation and decision logic
1. Preserve all raw OCR candidates, including low-confidence and conflicting candidates.
2. Compare outputs by field, not only by whole screenshot.
3. Calibrate confidence separately for each engine and field. Scores from different engines are not inherently comparable.
4. Engine agreement is supporting evidence, not proof of truth. Disagreement is a review signal; agreement can still be wrong.
5. Validate type, permitted format, separators, ranges, expected identity, field boundaries, and cross-field consistency.
6. Keep raw string, parsed representation, selected value, and review/correction value in separate fields.
7. Never silently convert an ambiguous digit, change a player/ship name, replace one damage/XP value with another, or choose the most plausible-looking candidate.
8. Fuzzy dictionaries/reference lists may suggest candidates, flag suspicious strings, or support review; they must not automatically replace player names, ship names, or numerical values.
9. If no candidate is sufficiently supported, return unavailable/uncertain/conflicting/rejected and request or queue review rather than inventing an accepted value.
10. Log the source candidate, proposed parse/correction, validation outcome, rationale, reviewer decision if any, and timestamp.

Step 7 — Structured battle records and provenance
Each record should include, as applicable:
- Schema version and job identifier.
- Source filename, media type, dimensions, SHA-256, and original Discord message/attachment references.
- Screenshot classification and layout profile.
- Field identifiers and field types.
- All raw candidates and engine/version/model/configuration information.
- Confidence where supplied by the engine, original polygons, ROI coordinates, crop/variant, timestamp, and preprocessing provenance.
- Parsed value, selected value (if any), validation status, review status, reason, and audit trail.
- Original value, corrected value, reviewer, decision, and timestamp for any authorized manual correction.

Store accepted values separately from recognition evidence. Preserve provenance through pending manual corrections, final exports, and Discord output.

Step 8 — Human review
Route to review when engines disagree, confidence fails calibrated policy, localization is uncertain, numeric parsing fails, identity is ambiguous, required fields are absent, cross-field checks fail, or a candidate is suspicious.

The reviewer must be able to see the original screenshot, highlighted ROI, raw engine candidates, confidence, validation reason, and history. Provide approve, correct, reject, and defer/review-later actions as appropriate. Record reviewer identity, authorization/role, old and new values, reason, and timestamp. Unapproved values must not enter approved exports. Never overwrite original OCR evidence with a reviewer correction.

A web dashboard is optional; the existing Discord workflow should remain the primary integration unless a dashboard is justified and implemented.

Step 9 — Discord integration
1. Reconcile against the existing bot commands, events, submission flow, OCR invocation, parsing, formatting, error recovery, and data structures.
2. Integrate through the bot's existing supported interfaces; do not impose an untested new folder tree or replace the Node.js architecture with a Python-only application.
3. Preserve ordinary bot operations and report failures accurately.
4. Test screenshot submission, recognition invocation, result return, errors, and normal Discord operation as a separate smoke-test gate.

12. DATASET, METRICS, AND MEASURABLE IMPROVEMENT

1. Build a labeled WoWS screenshot dataset with field-level ground truth and stable image identifiers.
2. Classify cases by screen type, resolution/UI scale, screenshot quality, field category, and known failure mode.
3. Keep training/tuning and held-out evaluation sets separate where applicable. Never optimize solely against the held-out acceptance set.
4. Record baseline Tesseract.js output before changing preprocessing, localization, or engine behavior.
5. Compare Tesseract.js and PaddleOCR under identical crops, inputs, and controlled settings.
6. Measure:
   - Character Error Rate (CER) and Word Error Rate (WER), using edit/Levenshtein distance against ground truth.
   - Exact-match accuracy for player names, ship names, numeric fields, and other exact fields.
   - Field coverage/completeness.
   - Incorrect acceptance rate (wrong values accepted as valid).
   - Rejection/review rate and candidate disagreement rate.
   - Localization accuracy/IoU.
   - Processing time by stage, throughput, and end-to-end latency.
   - Peak RAM, GPU memory/utilization when enabled, worker utilization, and queue depth.
7. Exact-match accuracy and incorrect acceptance are particularly important. Do not optimize CER/WER alone if a system begins accepting incorrect battle statistics.
8. Produce side-by-side comparisons of original screenshot, crop, preprocessing variants, engine outputs, validation decisions, and expected values.
9. Keep every experiment reproducible by recording engine version, model, crop coordinates, preprocessing parameters, and test dataset version.

13. FAILURE-ANALYSIS LABORATORY

For each failed or suspicious field, retain:
1. Original screenshot and checksum.
2. Expected ground-truth value.
3. Screenshot type/layout and resolution/UI scale.
4. Localization coordinates and crop.
5. Each preprocessing variant.
6. Raw output from every OCR engine.
7. Confidence and engine metadata.
8. Parsing/validation result and reason.
9. Failure category and root cause.
10. Corrective change and before/after comparison.
11. Targeted and regression results.

Classify failures at least as:
- Input/file decoding or ingestion failure.
- Screenshot classification/layout-profile failure.
- ROI localization/cropping failure.
- Preprocessing failure.
- Recognition/model/API failure.
- Reading-order/row/column assignment failure.
- Parsing or field-schema failure.
- Exact-value validation/decision failure.
- Unsupported/ambiguous source evidence.
- Worker timeout, queue, concurrency, memory, or resource failure.
- Persistence, export, Discord integration, or deployment failure.

The lab should generate a report with original screenshot, selected crops, processed variants, raw recognition, expected values, failure category, cause, and corrective result. Detect both unreadable values and confidently accepted but incorrect values.

16. BOUNDED FILE UPLOADS AND STREAMING

A previous design used a 25 MB upload check; another example discussed 15 MB/50 pages for a generic document-processing service. These are proposals for different contexts, not one universal limit. Inspect actual requirements and configure explicit byte, page-count, image-pixel, and processing-time limits.

Required sequence:
1. Validate declared size and actual streamed byte count.
2. Read incrementally (a 64 KiB chunk was proposed), calculate SHA-256 as chunks arrive, and write to a controlled staging file.
3. Validate content by decoding/format inspection rather than trusting the filename or MIME header alone.
4. Enforce byte, page, frame, pixel, and decompression limits.
5. Hand the worker a stable file reference, job ID, and checksum instead of a giant in-memory byte array.
6. Process pages lazily, one at a time, where the document profile needs multipage input.
7. Clean staged files after success/failure, and periodically recover abandoned files.
8. Do not perform chunked validation and then call a full-buffer read that loads the entire upload back into RAM.
9. Be aware that `pdf2image.convert_from_bytes()` may return all page images in memory; prefer bounded page processing/output-folder or streaming approaches where applicable.

17. OCR MODEL LIFECYCLE AND CONCURRENCY

The initial safe production baseline is:
1. One OCR model instance per worker process.
2. One active inference operation initially, with a bounded pending queue.
3. Explicit timeout, task ownership, process shutdown, restart recovery, and resource monitoring.
4. CPU and GPU worker profiles configured independently.
5. Benchmark safe alternatives before introducing multiple model copies or a general thread-safe pool.

`asyncio.to_thread()` moves blocking inference off an event loop; it does not prove the OCR model is thread-safe and does not automatically increase throughput. Avoid simultaneous calls on one shared model unless its library/runtime explicitly supports that pattern and tests confirm it. Only introduce a `queue.Queue` model checkout pool after memory, concurrency, and performance tests justify multiple instances. For GPU setups, one worker process per assigned GPU is a possible initial operating model, not an unconditional requirement.
