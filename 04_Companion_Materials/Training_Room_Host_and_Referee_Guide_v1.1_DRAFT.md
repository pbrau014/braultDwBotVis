## 2. Before opening the room

<div style="background-color:#DFF2FF; border:1.5px solid #0070C0; padding:6px 8px; margin:4px 0;"><strong>⚓ Quick hint:</strong> Treat this as practical guidance, not an event rule; verify game mechanics against current evidence.</div>
1. Read the approved event settings and match fixture. Record the match/game ID, host, fallback host, map, mode, duration, ship/tier restrictions, sides/spawns, lineup visibility, observers and setting version.
2. Confirm that the selected event format permits the planned lineup and room settings. Pilot lineup visibility may differ from the recurring format; do not apply one format’s exception to the other.
3. Check that a fallback host can create or modify the room if the assigned host fails. Verify each team representative and the referee contact are present.

## 3. Create and configure

<div style="background-color:#DFF2FF; border:1.5px solid #0070C0; padding:6px 8px; margin:4px 0;"><strong>⚓ Quick hint:</strong> Confirm eligibility, identity, and roster against the selected format before match setup.</div>
1. From Port, open the battle-type selector beside the BATTLE! control and locate Training. The current wiki describes this selection path; exact labels or location may vary by client build.
2. Use the client’s room-creation action. Set the map, battle mode, duration, available ship/tier/nation limits, room visibility/password if provided, and any approved description. Do not guess missing controls; record an item as not available and escalate if it is required by the fixture.
3. Assign participants to the published sides and use the selected format’s visibility rule. Confirm team slots, observers and team leaders if used. Do not add bots or observers unless this event allows them.
4. Capture a host-side room/settings image or record where the approved procedure requires it; do not post passwords or private room credentials publicly.

## 4. Two-side verification and ready-up

<div style="background-color:#DFF2FF; border:1.5px solid #0070C0; padding:6px 8px; margin:4px 0;"><strong>⚓ Quick hint:</strong> Verify room configuration and both sides’ readiness before starting; record exceptions as they occur.</div>
1. Read the fixture aloud or post the game ID so everyone is checking the same match.
2. Both team representatives independently verify map, mode, duration, sides/spawns, legal lineup, visibility, player slots and observer permissions.
3. Resolve any objection before ready-up. If the installed client cannot represent an approved setting, do not silently approximate it; pause and contact the referee.
4. Record both representatives’ confirmation and the actual start time. Start only when the room matches the approved settings and both sides are ready.

## 5. Clocks, restarts and faults

<div style="background-color:#DFF2FF; border:1.5px solid #0070C0; padding:6px 8px; margin:4px 0;"><strong>⚓ Quick hint:</strong> Apply the declared clock and restart rule for this event; record the trigger, time, and decision.</div>
1. Use separate timestamps for scheduled start, attendance deadline, between-game deadline, restart request, restart approval and restart completion. Never use one clock to infer another.
2. Check the selected ruleset’s restart quota and request cutoff. For the Pilot source baseline, requests are made within the first two minutes, completion window is five minutes, and each team has one ordinary restart. The recurring format’s quota varies by series length and must be published.
3. Record reason, screenshot/replay evidence, requesting side, game clock, rule applied, quota impact, permitted lineup change, ruling official and final disposition.
4. If the cause may be an official/platform fault, preserve evidence and request a ruling. An extension is not automatic; it must be allowed by the published rule or recorded as an authorized emergency action.

## 6. Close the game

<div style="background-color:#DFF2FF; border:1.5px solid #0070C0; padding:6px 8px; margin:4px 0;"><strong>⚓ Quick hint:</strong> Apply the declared clock and restart rule for this event; record the trigger, time, and decision.</div>
1. Confirm the match/game ID and result screen are consistent with the official fixture.
2. Ensure each participant submits required original evidence and that replay capture/retention matches the event policy. The recurring source baseline is to preserve replays for at least 48 hours, subject to the approved retention setting.
3. Record incidents, accepted metric corrections, disputes, the scoring calculation, and the final verified match outcome. Link the outcome to its participant-level inputs and outputs; record awards as separate decisions.
4. For recurring bracket play, advance from the verified match outcome calculated from the published individual-performance metrics under the approved scoring method, applying the D21 tie-break hierarchy where needed. Do not use a raw participant `dblns` value alone unless the published formula expressly specifies that use.
