## Phase 3 — Prove and correct sequential OCR, timeout, cancellation and cleanup

**Status: IMPLEMENTED; LOCAL ACCEPTANCE PARTLY PASSED; HISTORICAL ROOT CAUSE AND TARGET-WINDOWS VALIDATION OPEN.** The current source adds operation watchdogs for Tesseract.js `setParameters` and `recognize`, waits for the actual underlying worker thread termination result on timeout, and runs each image in a separately supervised child process. The parent imposes an independent image deadline, kills the child tree on timeout, and waits for the `close` event before advancing. Tests for a stuck operation, worker-termination confirmation, fail-closed behavior, real hanging child cancellation, and queue recovery passed in the contract suite. Three five-image network-blocked runs passed 5/5 each; the two image orders passed 2/2 each; and the separate four-image Tesseract.js run passed 4/4. However, the historic pass-16 stall is not proven to have a single identified root cause. An integrated injected stall through an actual Tesseract.js recognition pass followed by a successful real-image recovery, plus the target Windows Node.js 24 run, remains necessary before this phase is fully closed.

This phase must establish a reliable explanation for the historical stall on the second image at recognition pass 16. Do not assume that it is caused by worker termination unless the evidence supports that conclusion.

### 3.1 Instrument the complete lifecycle

Capture run ID, image job ID, queue position, worker initialization, each OCR pass, crop type, crop dimensions, PSM, preprocessing settings, recognition start/end, timeout firing, termination request, confirmed termination, promise settlement, parsing, validation and report writing.

Capture the last completed operation before a stall. Avoid exposing credentials or unnecessary user data in routine logs.

### 3.2 Reproduce the sequential problem

Run the Hoffmann and Asashio fixtures in both orders, then the four-image batch, then the five-image batch.

Repeat each required sequential scenario at least three times. Compare with separate-process executions of the same fixtures.

Inject a controlled stall at the first, middle and last recognition pass. Verify that the timeout fires and that the failed task cannot overlap a subsequent task.

Identify whether any stall originates in recognition, parameter updates, event-loop behavior, preprocessing, parsing, report writing, cleanup or the outer test runner.

### 3.3 Implement robust cancellation

Review the actual Tesseract.js 6.0.1 worker and termination code.

If its termination API cannot establish that the underlying worker has exited, implement the smallest safe alternative. A separately supervised per-image OCR child process is acceptable if needed, provided the parent can enforce an independent deadline and wait for the child to close.

The job queue must:

- Have a bounded backlog.
- Report queue position and explicit overflow.
- Use per-operation and per-image deadlines.
- Kill and wait for the stalled worker/process.
- Confirm closure before starting another image.
- Settle pending promises and release resources.
- Halt and report a fatal error if cancellation cannot be confirmed.

Do not simply race recognition against a timer and assume the underlying computation stopped.

### 3.4 Phase 3 acceptance criteria

- A forced 30-second timeout produces an explicit application-level timeout within a documented deadline plus cleanup grace period.
- Worker/process termination is confirmed.
- A subsequent image succeeds after an ordinary timeout with successful cleanup.
- No subsequent image starts while the prior worker is still active.
- Both image orders and three consecutive sequential batches pass.
- A cleanup failure stops the queue safely.
- No timeout silently creates an incomplete correction workflow or a false successful record.

Begin with a 90-second per-image diagnostic budget and a provisional three-minute batch target, then measure performance on the target Windows machine before making production settings permanent.
